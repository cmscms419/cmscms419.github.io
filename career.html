Project 01
2023.01 — 2023.12
엔진 온보딩 &
그래픽스 학습
분석 · 학습
기술 스택
C C++ OpenGL ES 3.0 CMake WSL/Ubuntu
배경

엔진팀 입사 초기 온보딩 과정으로, 자체 그래픽 엔진의 코드베이스를 파악하고 OpenGL ES 3.0 기반 렌더링 원리를 학습하는 것이 주된 업무였다. 이 기간은 이후 실제 제품 개발에 참여하기 위한 기반을 쌓는 시기였다.

담당 업무
  • 자체 그래픽 엔진 코드베이스 분석 — 렌더링 파이프라인 흐름 파악
  • WSL/Ubuntu 환경에서 CMake 빌드 환경 구성 및 가이드 작성
  • OpenGL ES 3.0 기반 그래픽스 개념 학습 (셰이더, 버퍼, 렌더링 루프 등)
  • 코드 분석 중 발견한 버그 검출 및 리포트
회고
그래픽스를 처음 접하는 시기였다. 코드를 읽으면서 렌더링 파이프라인의 전체 구조를 파악하는 것이 생각보다 오래 걸렸고, 이론과 실제 코드 사이의 간격을 좁히는 데 많은 시간을 투자했다. 이 기간의 학습이 이후 실무 프로젝트들의 토대가 됐다.

차량 전시용 3D 인터랙티브 데모

Project 02
2024.08 — 2025.02
3D 차량
전시 데모
설계 · 개발
기술 스택
C C++ OpenGL ES 3.0 CMake
설계 고민
기획 단계에서 색상 변경, 트윈 애니메이션, 화면 전환 등 여러 동작이 동시에 작동해야 한다는 요구사항이 있었다. 어떤 구조로 만들어야 이 조건을 깔끔하게 충족할 수 있을지 고민이 필요했다.
설계 결과
check/update 단계 분리로 상태 검사와 갱신의 책임을 나누고, 각 동작을 독립 클래스로 구현했다. 데이터 주도(Data-Driven) 구조를 도입해 오브젝트 속성 값만 설정하면 해당 동작이 자동 적용되도록 설계했다.
담당 업무
  • 이벤트 처리 구조 설계 — check(상태 검사) / update(갱신) 단계 분리
  • 색상 변경, 트윈 애니메이션, 화면 전환 등 5종 이상의 동작 클래스 구현
  • 데이터 주도 방식 도입 — 오브젝트 속성 설정만으로 동작 자동 적용
  • 그래픽 엔진 위에서 인터랙션 레이어 독립적으로 구현
성과
  • 디자이너가 오브젝트 정보만 설정하면 동작 자동 적용 — 개발자 개입 최소화
  • 새로운 동작 추가 시 기존 클래스를 상속해 확장만 하면 됨 — 유지보수 비용 절감
기술 선택 이유
check/update 분리는 상태 검사와 상태 갱신의 책임을 명확히 하여 복잡한 인터랙션에서 버그 원인을 추적하기 쉽게 만들기 위한 선택이었다. 데이터 주도 설계는 디자이너와 개발자의 작업 경계를 분리하여 디자인 변경이 코드 수정 없이 반영되도록 하기 위해 채택했다.
회고
구조 설계가 코드 품질보다 더 큰 영향을 미친다는 것을 실감했다. 내가 만든 동작 클래스를 예시 코드로 제공하고, 팀원이 그것을 참고해 기능을 추가하는 방식으로 협업했다. 패턴이 명확하니 코드 리뷰 비용이 줄었고, 아키텍처 결정이 협업 방식에도 직접 영향을 준다는 것을 경험했다.

VP Demo Car 차량 클러스터 GUI 개발

Project 03
2025.08 — 2026.04
차량 클러스터
GUI
GUI 개발
기술 스택
C C++ OpenGL ES 3.0 CMake
AS-IS — 문제 상황
CAN 신호는 한 번에 여러 신호가 묶음으로 들어오는데, 그 중 실제로 값이 변경된 신호만 GUI에 반영되어야 했다. 또한 위젯 수가 많았기 때문에 각 위젯이 동일한 코드 구조를 따르도록 설계해야 유지보수가 가능했다.
TO-BE — 역할 분담
선임이 CAN 데이터 매니저(신호 수신·분배 레이어)를 구축했고, 나는 그 아래 GUI 레이어의 구조를 담당했다. 변경된 신호만 위젯에 전달되도록 연결하고, 모든 위젯이 동일한 패턴으로 신호를 받아 렌더링하는 구조를 설계·구현했다.
담당 업무
  • Speedmeter, Telltale, ADAS Info, TBT(Turn-By-Turn) 등 약 10개 영역의 2D GUI 위젯 담당
  • CAN 신호 50~80개 중 변경된 신호만 감지해 해당 위젯에 반영하는 구조 구현
  • 모든 위젯이 동일한 코드 구조를 따르도록 GUI 레이어 설계
성과
  • 사양 변경 대응 기간 평균 하루 이내로 단축
  • 통일된 위젯 구조로 신규 위젯 추가 및 유지보수 용이
기술 선택 이유
하드웨어와 소프트웨어 스택은 계약 사양에 미리 지정되어 있었다. C/C++, OpenGL ES 3.0 모두 선택이 아닌 주어진 환경이었다.
회고
차량용 임베디드 환경에서 그래픽스 개발을 처음 경험했다. 선임이 만든 데이터 레이어 위에서 GUI 구조를 설계하면서 레이어 간 역할 분리가 실제로 어떻게 작동하는지 직접 경험했다. 같은 패턴을 위젯 전반에 적용하는 과정에서 일관된 구조가 유지보수에 미치는 영향을 실감했다.

외부 데이터센터 POC — 3D 시각화

Project 04
2025.03 — 2025.04
3D 데이터센터
시각화
성능 최적화 · 개발
기술 스택
React TypeScript Three.js React Three Fiber Drei Jotai Vite
AS-IS — 문제 상황
최대 2,250개의 서버 랙 인스턴스를 개별 Mesh로 렌더링하면서 GPU에 draw call이 인스턴스 수만큼 발생했다. 결과적으로 30fps 병목이 생겨 실시간 모니터링 목적에 적합하지 않았다.
TO-BE — 해결 방법
Three.js InstancedMesh와 Custom Shader를 적용해 같은 geometry를 공유하는 인스턴스를 단일 draw call로 묶어 GPU에 전달했다. 결과적으로 30fps → 55~60fps로 약 2배의 성능 개선을 달성했다.
담당 업무
  • React Three Fiber 기반 3D 데이터센터 시각화 구현
  • 최대 2,250개 인스턴스 실시간 렌더링 환경 설계
  • InstancedMesh + Custom Shader 적용으로 draw call 최소화
  • Jotai 상태 관리로 대용량 오브젝트 상태 처리
성과
  • 렌더링 성능 30fps → 55~60fps (약 2배) 개선
  • 인스턴스 수 증가에도 안정적인 프레임 유지
기술 선택 이유
React, React Three Fiber 등 프론트엔드 스택은 계약 업체에서 지정한 환경이었다. InstancedMesh는 동일한 geometry를 가진 대량 오브젝트를 단일 draw call로 처리하는 Three.js의 핵심 최적화 기법으로, 렌더링 병목의 직접적인 해결책이었다.
회고
웹 3D 렌더링 성능 최적화의 핵심이 draw call 최소화라는 것을 수치로 직접 확인했다. C++/OpenGL 기반 임베디드 그래픽스와 JavaScript/WebGL 기반 브라우저 3D는 API가 달라도 GPU 병렬 처리 원리는 같다는 점을 실감했고, 기술 스택을 넘나드는 그래픽스 원리에 대한 이해가 깊어진 프로젝트였다.
